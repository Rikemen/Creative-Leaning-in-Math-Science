**Firebase Hostingで配信し、ゲームはブラウザ内で動かす。ゲストは端末内に記録、メール確認済み会員はFirestoreに記録する。ランキング対象の結果はCloud Functionsを通して確定する。**

## 2. システムの構成と責務

| 構成要素 | 役割 | 保存するもの／しないもの |
| --- | --- | --- |
| Firebase Hosting | HTML・JS・CSS・画像・音のHTTPS配信 | ゲームの配布ファイル。記録DBとして使わない |
| ブラウザ：p5.js＋ml5.js | 描画、カメラ姿勢推定、問題進行、効果音、即時フィードバック | カメラ画像・関節座標はメモリ内のみ |
| IndexedDB | ゲストの設定・履歴、会員の未送信結果 | 端末内記録。本人認証やランキングの証拠にはしない |
| Firebase Authentication | メール／パスワード、メール確認、再ログイン、パスワード再設定 | メールと認証情報の正本。Firestoreにパスワードを置かない |
| Cloud Firestore | アカウント、プレイヤー、履歴、集計、競技設定、ランキング | メールを公開データへ複製しない |
| Cloud Functions（Callable） | 所有者とメール確認、結果整合性検証、集計、ランキング更新 | Admin SDKで保存。権限判定をサーバーにも実装 |
| Firebase App Check | 対象APIへの正規アプリ由来のアクセス確認 | 身体操作や計算の正しさを保証するものではない |
| Authメールリンク＋受信箱 | 確認メールとパスワード再設定 | Firebase Authのフローで扱い、独自メールサーバーを作らない |

HostingはSSLとCDNを提供し、静的ゲームをそのまま配信できる。[Firebase Hosting公式](https://firebase.google.com/docs/hosting)

通信経路は、ブラウザ→HostingがHTTPS GET、ブラウザ→AuthがFirebase Auth SDK、ブラウザ→FirestoreがWeb SDK（Rules適用）、ブラウザ→FunctionsがCallable HTTPS（IDトークン＋App Check）、Functions→FirestoreがAdmin SDK、ブラウザ→IndexedDBが端末内API。ゲームのカメラフレームをFunctionsへ送る経路は作らない。

FunctionsへCallableを使うとSDKが利用可能な認証／App Checkトークンを添付できる。[Callable公式](https://firebase.google.com/docs/functions/callable)

Cloud Storageは初期構成に含めない。固定の画像・音・アイコンはHostingで十分。将来ユーザー自身の画像アップロードが必要になった時に追加する。初版ではAnalytics、対戦サーバー、毎フレームのFirestore通信も不要。

## 3. ゲストと会員

| 状態 | 遊ぶ | 履歴 | ランキング参加 |
| --- | --- | --- | --- |
| ゲスト（未ログイン） | 全基本機能、カメラ／タッチ | このブラウザ内。削除・端末変更では復元不可 | 閲覧可、投稿不可 |
| 登録済み・メール未確認 | ゲスト同様に遊べる | 端末内。クラウド保存は確認後 | 閲覧可、投稿不可 |
| メール確認済み会員 | 基本機能＋記録ページ | プレイヤーごとにクラウド保存、別端末で復元 | 条件を満たす挑戦だけ参加可 |

### ゲストを匿名Authにしない理由

最初は**Firebase匿名認証を使わず、ローカルのゲストID**にする。ゲストのクラウド記録が要件にないため、匿名アカウントとFirestoreデータの寿命・統合作業を増やさずに済む。

将来「未登録でもクラウドへ保存」を追加する場合は匿名Authが候補。Firebaseは匿名アカウントへの認証資格情報のリンクを提供するが、既存メールアカウントとの衝突時のデータ統合は別途設計する。[Firebase匿名認証公式](https://firebase.google.com/docs/auth/web/anonymous-auth)

### 会員登録のフロー

1. 保護者がメールとパスワードで登録。Auth UIDを取得する。
2. 確認メールを送信。「確認が済むまで遊びながら待てる」画面にする。
3. 確認リンクから戻ったらユーザー情報を再読込し、IDトークンも更新する。URLパラメータだけで確認済みと扱わない。
4. `ensureAccount` がトークンの `email_verified` とAuth側の状態を確認。アカウントと最初のプレイヤーを冪等作成する。
5. 任意で「この端末の記録を取り込む」を表示。取り込み先プレイヤーを明示し、本人が選んだ履歴だけ送る。
6. ゲスト履歴は `source=guest_import, verification=unverified` として保存。既存会員の履歴へ追加し、既存のベスト記録を上書きしない。ランキングへ遡及投稿しない。

確認メールはFirebaseの `sendEmailVerification` を使う。[メール確認公式](https://firebase.google.com/docs/auth/web/manage-users)

共有端末では、ログアウト時に会員の表示キャッシュと購読をクリアし、ゲスト用保存領域へ戻す。未送信結果は元UIDに結びつけたまま残し、別アカウントへ自動送信しない。元アカウントの再ログイン後だけ再送する。

## 4. 保護者アカウントとプレイヤーを分ける

Authのユーザーは「ログインする人」、プレイヤーは「実際に遊んだ子供や大人」。**アカウント1件にプレイヤー複数件**を持てるモデルにして、初版UIでは1人だけを自動作成する。兄弟の選択画面は後から追加できる。

公開するのはゲーム用ニックネームと選択式アバター。実名・メール・年齢・顔写真はランキングに不要。初期値は非公開、保護者がランキング参加を選んだプレイヤーだけを掲載する。ニックネーム変更・公開停止はサーバー経由で公開行へ反映する。

## 5. 記録とランキングを分離する

### 通常プレイ

現在のロードマップどおり、有効プレイ時間60秒で一時停止可能。ゲストは端末保存、確認済み会員は `savePracticeRun` に結果を送信する。サーバーは所有者・型・範囲・重複を確認するが、記録の内容は自己申告扱い。オフライン時は端末で保存して後から再送できる。履歴には残るがランキング対象外。

### ランキング挑戦

公開ランキングを追加する段階で、専用の挑戦モードを導入する。

1. 準備・カメラ認識を終えてから `startRankedRun` を呼ぶ。サーバーがルール版・問題生成seed・プレイヤー・締切を固定したセッションを発行する。
2. `startsAt` を少し先に設定してカウントダウンし、`endsAt=startsAt+60秒`。サーバー時刻差を調整して画面に表示する。通信遅延で開始に間に合わない場合はそのセッションを使わず準備に戻る。
3. ゲーム判定はブラウザで即時に行う。命中区間・回答・問題順をメモリ内に記録する。フレームごとのネットワーク送信はしない。
4. 終了時に `finishRankedRun` へイベント列を送る。送信データに `score` があっても信用せず、サーバーがseed、問題、選択、命中時間、ポーズ解除イベントから得点を再計算する。
5. サーバーが実行結果、統計、ランキングのベスト1件をトランザクションで更新する。二重送信は同じ `runId` と内容ハッシュで同じ結果を返す。

サーバー側の受信期限は `endsAt+15秒` を仮値とし、プレイ時間そのものは延長しない。開始前送信、非単調時刻、重複区間、60秒外のイベント、理論上限を超える命中、別UID／別プレイヤー、過大ペイロードは拒否する。期限内の一時的な失敗だけ再試行し、それ以外は非ランキングの履歴として別途保存する。

**ランキング挑戦では、手動停止・タブ非表示・長い認識喪失・操作方式切替があればランキング対象外へ降格し、通常プレイとして続けられる**仕様を提案する。子供の遊びは中断させず、停止時間を使った熟考をランキング条件と混在させない。UIにも開始前に短く伝える。

これでも、改変されたブラウザによる架空イベント・自動解答・申告しない停止・別入力の偽装は完全に排除できない。`validated` は「サーバーがルールとの整合性を確認した」の意味で、実際の身体操作を証明した意味ではない。App Checkもその保証をしない。家族向けのカジュアルランキングを想定し、賞品付き大会レベルの公平性が必要ならサーバー逐次出題等を別設計する。

### 比較条件

`boardId` はサーバーで発行し、**ルール版×難易度×操作方式×期間**ごとに分ける。初版は全期間（all-time）のみ。タッチとカメラ、合計5以下と合計18以下、HPやヒント設定の異なる版は混ぜない。カメラ内でも照準方式が違えばルール版に含める。

1プレイヤー・1ランキングにベスト1行。第一順序は破壊枚数の降順。同点は同じ順位として表示し、表示順だけ達成日時の昇順、最後に公開IDで固定する。初版は上位50件だけ表示し、圏外の厳密順位や全件リアルタイム購読は持たない。

## 6. 信頼境界とデータ保護

- ブラウザの得点、UID引数、`emailVerified`、`isRanked` は信用しない。UIDは認証コンテキストから、登録確認は信頼済みトークンと必要に応じAuth正本から判断する。
- Firestoreのクライアント書き込みは初版ではすべて禁止。会員プロフィール変更もCallable経由。読み取りは「本人の非公開データ」「明示した公開ランキング」「公開ルール」だけ。
- Admin SDKはFirestore Rulesを迂回するため、Functions内で所有者、メール確認、削除中状態、許可フィールドを検証する。[Firestore RulesとサーバーSDK](https://firebase.google.com/docs/firestore/security/rules-query)
- FirestoreのRulesはフィルターではない。クエリのパス・絞り込み・limit・インデックスをまとめて定義し、実クエリでEmulatorテストする。同じ公式ページ参照。
- 保存失敗を「履歴0件」として表示しない。前の表示を保持し、「未同期」「再試行」を出す。Auth待ち・通信失敗・本当に空の状態を区別する。
- カメラ映像・音声・顔特徴・関節列はクラウドへ保存しない。ランキング検証用ログも数値の選択・時間だけ。メール・トークン・生ペイロードを通常ログに出さない。
- アカウント削除は再認証を要求し、まず削除中にして公開行を非表示／削除、配下データを再試行可能なジョブで削除、最後にAuthを削除する。親ドキュメント削除だけで完了にしない。

## 7. 運用・公開構成

ローカルはFirebase Emulator Suite、公開用は専用Firebaseプロジェクトを推奨。stagingを設ける場合も本番Auth／Firestoreとは分離する。HostingプレビューチャンネルだけではDBが分離されるとは考えない。

FunctionsとFirestoreのリージョンは日本の利用を想定して東京近傍を候補とするが、既存プロジェクトID・DB所在地・課金設定は未確認。作成時に対応リージョンを確認し、近い配置を選ぶ。クライアントにもFunctionsリージョンを明記する。

Functionsをデプロイする段階ではBlazeプランが必要。これは将来の構成要件で、今回課金設定を変更していない。[Functions導入公式](https://firebase.google.com/docs/functions/get-started)

毎フレーム保存せず、基本は1プレイ終了時に結果を保存。ランキング挑戦だけ開始時もAPIを呼ぶ。関数側のUID単位レート制限、ペイロード上限、最大インスタンス、App Check、課金アラートを設定する。予算アラートを自動停止装置とみなさない。公開ランキングは画面表示時の上位取得と明示的な更新を基本にする。

App Checkは計測してから本番適用し、正規端末が拒否されないか確認する。[CallableへのApp Check適用](https://firebase.google.com/docs/app-check/cloud-functions)

ゲーム用公開ディレクトリだけをHostingへ配信する。`system-design/`、制作元、テスト、Functionsソースを静的配信対象に含めない。Functions・Rules・indexを準備してから新しいフロントを公開し、旧版が動く移行期間を設ける。
