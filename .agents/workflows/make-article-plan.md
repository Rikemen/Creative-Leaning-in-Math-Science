# 学習記事設計HTMLドキュメント生成ワークフロー

## 目的

数学・理系学習記事をいきなり全文執筆せず、まず **「どのような記事にするか」** を設計するためのHTMLドキュメントを生成する。

このワークフローは、記事本文そのものではなく、記事の構成・狙い・読者体験・必要な概念イラスト/シミュレーション/練習問題を事前に固めるために使う。

## 基本方針

- 記事は「知識の羅列」ではなく、読者が **なぜそれを学ぶのか** から自然に入れる構成にする。
- 歴史的経緯だけでなく、後から見つかった応用、有用性、他分野との接続、一般化/特殊化の関係を整理する。
- 記事トップや導入部のビジュアルは、原則として抽象SVGではなく、概念を表す親しみやすいイラストとして設計する。
- イラスト生成が必要な場合は `.agent/workflows/generate-image.md` の統一テイストと承認手順に従う前提で、画像の描写・保存先・ファイル名案を記事設計段階で明確にする。
- 図解・表・グラフ・シミュレーションの候補を記事設計段階で明確にする。
- 各記事には原則としてシミュレーターを付ける。記事内容の性質上シミュレーター化が難しい場合のみ、理由と代替可視化を明記してスキップできる。
- 例題と練習問題は分ける。例題は解説付き、練習問題は読者が手を動かすためのものにする。
- 完成記事の実装前に、記事の流れ・必要素材・確認事項が一目で分かる状態にする。

## 出力先の命名規則

生成するHTMLファイルは `docs/article-plans/` ディレクトリに配置する。
ファイル名は **記事テーマを簡潔な英語に変換** し、`kebab-case` で命名したうえで、**生成日の日付サフィックス** を付与する。

### ルール

1. ユーザーから依頼された記事テーマを **簡潔な英語** に翻訳する
2. 英語タイトルを **kebab-case** に変換する
3. 生成日を `YYYYMMDD` 形式で取得する
4. 出力先を `docs/article-plans/{kebab-case-title}-{YYYYMMDD}.html` とする
5. `docs/article-plans/` ディレクトリが存在しない場合は作成する
6. 既存の同名ファイルがある場合は上書き前に確認する

### 命名例

| 依頼内容 | ファイル名（2026年6月15日に生成した場合） |
|---|---|
| 微分係数の記事設計 | `docs/article-plans/derivative-coefficient-20260615.html` |
| ε-δ論法の記事設計 | `docs/article-plans/epsilon-delta-definition-20260615.html` |
| 固有値と固有ベクトルの記事設計 | `docs/article-plans/eigenvalues-and-eigenvectors-20260615.html` |
| ベイズの定理の記事設計 | `docs/article-plans/bayes-theorem-20260615.html` |

## ベース仕様

**デザイントークン・基本スタイル・編集JS・モーダル・トースト** は `/make-lightblue-doc` ワークフロー（`.agent/workflows/make-lightblue-doc.md`）の仕様に準拠する。

サイドバー目次、ステータス管理付きテーブル、JSON入出力が必要な場合は `/make-dev-plan` ワークフロー（`.agent/workflows/make-dev-plan.md`）の仕様も流用してよい。

シミュレーター案を設計する場合は、必ず `.agent/workflows/make-simulator.md` を参照する。`EpsilonDeltaSimulator.vue` と `DerivativeSimulator.vue` のUI構成・状態設計・結果カード・記事ページ登録方式を基準に、専用コンポーネントにするか、`CalculusConceptSimulator.vue` の設定追加にするか、代替可視化にするかを記事設計段階で明記する。

## HTMLに必ず含めるセクション

生成する記事設計HTMLには、以下のセクションを必ず含める。

### 1. 記事概要

記事のテーマ、読者対象、記事のゴールを簡潔に書く。

必須項目:

- 記事タイトル案
- 対象読者
- 前提知識
- 読後にできるようになること
- 記事で扱わないこと

### 2. これから何を学ぶのか

今回の記事で扱う概念を、専門用語に入りすぎず短く説明する。

必須項目:

- 一言でいうと何か
- どんな場面で現れるか
- 最初に持ってほしい直感
- 読者が混乱しやすいポイント

### 3. なぜそれを学ぶのか

概念のモチベーションを掘り下げる。

必須観点:

- 何を解決するために生まれた/発見されたのか
- 歴史的経緯とは別に、後から見つかった有用な応用例はあるか
- 他の分野とどうつながるか
- 今回の話を内包する、より一般的な話はあるか
- 今回の話は、より具体的なものの一般化になっているか
- 学ばないと何に困るか

### 4. 概念イラストでイメージ

文章に入る前に、視覚的に理解するための概念イラスト案を設計する。

記事トップに置くビジュアルは、原則としてアプリ内で手書きする簡易SVGではなく、`.agent/workflows/generate-image.md` に従って生成する **概念イラスト** とする。数式やグラフそのものを正確に描く必要がある場合でも、単なる抽象線ではなく「読者が何を見ればよいか」が分かる教育的なイラストとして設計する。

必須項目:

- イラストの目的
- イラストに描く主体・構図・要素
- 読者に見てほしい変化/対応関係
- イラストのキャプション案
- `.agent/workflows/generate-image.md` に渡す英語プロンプト案
- 画像ファイル名案（例: `src/assets/article-illustrations/{slug}-concept.png`）
- 画像生成が不要/不適切な場合の理由と代替図解

### 5. 解説の流れ

本文解説の章立てを設計する。

推奨構成:

1. 直感的な説明
2. 最小限の定義
3. 記号や式の意味
4. 重要な性質
5. よくある誤解
6. 次の概念への接続

各章には「読者に何を納得してもらうか」を必ず書く。

### 6. 具体例で練習

解説の直後に、手順付きの具体例を設計する。

必須項目:

- 例題の問題文
- 解法のステップ
- 各ステップで使う考え方
- 途中式や図の入れ方
- 読者が間違えやすい点

### 7. グラフ・表・図式・シミュレーション

直感理解を強めるためのインタラクションや可視化を設計する。

シミュレーター設計は `.agent/workflows/make-simulator.md` に従い、既存の ε-δ シミュレータ・微分係数シミュレータのデザイン/システムパターンを優先して流用する。

必須項目:

- 原則として実装するシミュレーターの有無
- 実装方式（専用Vueコンポーネント / `CalculusConceptSimulator.vue` への設定追加 / フォールバック・代替可視化）
- グラフ/表/図式/シミュレーションの種類
- 入力パラメータ
- 初期値
- 出力・可視化する値
- 読者が操作して気づくべきこと
- 実装する場合の候補コンポーネント名
- `ArticleDetail.vue` での登録方法
- 実装しない場合の具体的な理由
- 実装しない場合の代替イラスト・表・静的図

### 8. 練習問題

読者が自分で解く問題を設計する。

必須項目:

- 基本問題
- 標準問題
- 発展問題
- ヒント
- 解答の方針
- 記事本文への戻り先

### 9. まとめ

記事の最後に残すべき要点を設計する。

必須項目:

- 3〜5個の重要ポイント
- 今日できるようになったこと
- 次に学ぶべきテーマ
- 関連記事候補
- FAQ化するとよい疑問

### 10. 素材・実装メモ

記事を実装する前に必要な素材と技術的な確認事項を整理する。

必須項目:

- 必要な補助図解素材
- 必要な概念イラストと生成プロンプト
- 必要なスクショ
- 必要な音声
- 必要なシミュレーション
- 追加する記事slug案
- 追加/変更する想定ファイル
- 未確定事項

## コンテンツ生成ルール

- 断定できない歴史・応用・分野接続は「要確認」と明記する。
- 高度な一般化は、読者の前提知識を超える場合でも「先にある大きな話」として短く紹介する。
- 数式は必要最小限から始め、記号の意味を必ず説明する。
- 記事トップのビジュアルは、原則として簡易SVGではなく概念イラストとして設計する。
- 概念イラスト案は「何を描くか」だけでなく「何を見てほしいか」まで書く。
- 概念イラストが必要な場合は `.agent/workflows/generate-image.md` を参照し、統一テイストに沿った英語プロンプト案、保存先、ファイル名案を必ず書く。
- 数学的に厳密なグラフは記事本文やシミュレーター側で扱い、トップイラストでは直感と概念の入口を優先する。
- 例題は必ず解説付きにする。
- 練習問題は解答を全部書きすぎず、ヒントと方針を分ける。
- まとめは新しい概念を増やさず、本文の要点に限定する。
- 記事実装が必要な場合でも、このワークフロー内では本文実装に入らない。まず記事設計HTMLの完成を優先する。

## 品質チェックリスト

- [ ] 何を学ぶ記事か一目で分かる
- [ ] なぜ学ぶのか、読者のモチベーションが明確
- [ ] 応用例・他分野との接続・一般化/特殊化の関係が整理されている
- [ ] 概念イラスト案があり、何を見せるイラストなのか明確
- [ ] イラスト生成が必要な場合、`.agent/workflows/generate-image.md` 用のプロンプト案・保存先・ファイル名案がある
- [ ] 解説の章立てが自然な順番になっている
- [ ] 具体例が手順付きで設計されている
- [ ] 原則としてシミュレーター案がある
- [ ] シミュレーター案が `.agent/workflows/make-simulator.md` の入力・出力・気づき・登録方法を満たしている
- [ ] シミュレーターをスキップする場合、理由と代替可視化が明記されている
- [ ] 練習問題が基本・標準・発展に分かれている
- [ ] まとめが3〜5個の要点に収まっている
- [ ] 必要素材と未確定事項が明記されている
- [ ] `data-section` 属性値が全セクションで一意である
- [ ] JSONエクスポート/インポートを入れる場合、往復可逆になっている

## 生成時の注意

- ブラウザサブエージェントによる自動確認は不要。
- 生成後のHTML表示確認はユーザー自身が `file://` で開いて目視確認する運用とする。
- エージェントはHTMLファイルの生成完了をもってタスク完了としてよい。
