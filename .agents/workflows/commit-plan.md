# Commit Splitting Planner (日本語)

**トリガー:** `/commit-plan`

**説明:**
作業ツリー全体（staged / unstaged / 未追跡）の未コミット変更を把握し、
**論理的に独立した最小単位**へ分割した `git add` / `git commit` の実行計画を立案する。
計画をユーザーに提示して**承認を得てから**、各単位を順次ステージ＆コミットする。

> **⚠️ このワークフローはファイルをステージ・コミットします。**
> 読み取り専用の `/commit`・`/commit-ja`（メッセージ生成のみ）とは異なり、
> 本ワークフローは **`git add` と `git commit` を実際に実行**する。
> ただし **STEP 4 の承認ゲートを通過するまで一切の add/commit を行わない**。
>
> **スコープに関する注記:** コミットメッセージの形式は
> `.agent/rules/git-commit-rules.md` に従う。一方で、同ルールの「対象は staged 変更のみ」
> という記述はメッセージ単体生成時のスコープ規定であり、本ワークフローは
> **分割計画の立案のため作業ツリー全体（unstaged・未追跡を含む）を分析対象とする**
> （ステージ先を計画するには全変更の把握が前提になるため、意図的に拡張している）。

---

## 1. 作業ツリー全体の把握

- **目的:** コミット対象となる全変更を漏れなく把握する。
- **アクション:**
  - `git status --short` で変更ファイル一覧（staged/unstaged/未追跡）を取得する。
  - `git diff --stat HEAD` で tracked 変更の規模を、`git ls-files --others --exclude-standard` で未追跡ファイルを確認する。
  - 必要に応じて `git diff HEAD -- <path>` で各ファイルの中身を確認し、変更の意図を読み取る。
  - **変更が一切ない場合:** 「未コミットの変更がありません。」とだけ返答して終了する。

## 2. 論理単位への分割（グルーピング）

- **目的:** 「1コミット1論理変更」を満たす、なるべく細かい単位へ分割する。
- **分割方針:**
  - **type を混在させない。** `feat` / `fix` / `docs` / `refactor` / `chore` などが混ざる変更は別コミットへ分割する。
  - **機能（feature）単位でまとめる。** 1機能の専用ファイル（view・data・component）は1つのコミットにまとめる。
  - **依存順に並べる。** 共通基盤 → 各機能 → 画面の配線（router/menu 等） → ドキュメント → ギャラリー登録、の順を基本とする。後のコミットが前のコミットに依存する向きにする。
  - **既存の前例に倣う。** このリポジトリは機能単位の細かいコミットを実践している（例: `feat(orchestra-erp): add lost-order management`、配線は `wire new screens into router`、計画書は `docs(gallery): ...` を別コミット）。同じ粒度・scope 命名に揃える。
- **部分ステージ（hunk 分割）の扱い:**
  - 1つのファイルが複数の論理単位にまたがる場合（例: `router/index.ts` や `menu.ts` に複数機能のエントリが同居）、**原則そのファイルはまとまった1コミット（配線コミット等）として扱い**、その旨を計画に注記する。
  - どうしても hunk 単位で分けたい場合は `git add -p` が必要になるが、**本環境では対話的ステージは使えない**ため自動実行はしない。その場合は計画にその制約を明記し、手動対応（ユーザーが `git add -p` を実行）に委ねる。

## 3. 各コミットのメッセージ生成

- **目的:** 各単位にそのまま使えるコミットメッセージを割り当てる。
- **アクション:**
  - `.agent/rules/git-commit-rules.md` のすべてのルールに従う（Conventional Commits、絵文字・曖昧語の禁止等）。
  - **言語:** description は**日本語**、type は英語のまま。
  - **scope:** 機能／領域名（例: `orchestra-erp`, `gallery`）を付与する。
  - **Description:** 50文字以内、末尾ピリオドなし、簡潔な業務調。
  - **Body（任意）:** 変更の意図・背景・影響を簡潔に。複数行は適切に改行する。

## 4. コミットコマンドの提示（ユーザー実行依頼）

- **目的:** 立案した計画をユーザーが自身のターミナルでそのまま実行できるように、一連のコマンドブロックとして提示する。
- **アクション:**
  - 計画された各コミット単位について、以下のコマンドを連続して実行できる Bash 用のコードブロック（```bash）として出力する。
    - `git add <files>`
    - `git commit -m "<件名>" -m "<本文>" -m "Co-Authored-By: <モデル名> <メールアドレス>"` のように、`-m` オプションを複数並べることで複数行のコミットメッセージ（件名・本文・フッター）を表現する形式を使用する。
      - **理由:** ヒアドキュメント（`<<'EOF'`）はシェルのペースト挙動により誤動作しやすく、コメント行での `===` の使用は zsh の `=command` 展開機能と競合して `zsh: == not found` エラーを引き起こしやすいため、これらは使用を避ける。
      - コメント行は単純に `# 1. タイトル` のように記号の連続（`===` など）を含めない。
  - **重要:** エージェント環境（サンドボックス）では `git commit` 等の権限が制限されている場合が多いため、**エージェント自身はコマンドの実行を行わず、ユーザーにコピー＆ペーストでの実行を依頼して終了する。**


---

**安全規定:**
- エージェントは `git add` や `git commit` を自動実行してはならない（ghost action の禁止および権限制約の回避）。
- 既存のステージ済み変更がある場合は、それも計画に含めるか明示的に扱いを確認する。
- `git commit -a` や `git add -A` のような無差別ステージは使わず、**計画した対象ファイルのみを明示的に add** するコマンドを生成する。
