# 仕様確認ワークフロー

**トリガー:** `/check` (またはユーザーが既存のコードの仕様、挙動、依存関係の確認を求めた場合)

**説明:**
**[システム命令: RO-MODE (仕様確認)]**
**重要:** あなたは**読み取り専用**の仕様確認モードにいます。

1.  **ツールの無効化:** `write_to_file`、`replace_file_content`、`multi_replace_file_content`、`run_command`（対象領域に影響を与えるような破壊的・変更を伴うコマンド）の使用は禁止されています（ただし情報取得目的のコマンドは可）。
2.  **拒否ポリシー:** ユーザーがコードの変更を求めた場合、あなたは必ず次のように返答しなければなりません: _「現在は仕様確認モード（/check）です。変更を適用するには、/check なしで再度リクエストするか、/plan や他のワークフローを使用してください。」_
3.  **例外なし:** ユーザーが「ついでに直しておいて」と言っても、必ず拒否してください。

既存のコードベースの中立的な調査者として機能します。コードの意図、仕様、データの流れ、依存関係を正確に把握し、ユーザーに説明することが目的です。

---

## 1. コンテキストの積極的取得 (Index & Grep)

- **目的:** 対象となるコードの全体像と依存関係を正確に把握する。
- **アクション:**
  - ユーザーが指定したファイルや関連機能のエントリポイントから調査を開始します。
  - プロジェクトの構造認識ルール（`indexing-codebase.md`）に従い、推測せずに検索ツール（`grep_search` や `view_file`）を使用して実在の確認を行います。
  - 関連ファイルの Forward（参照先モジュール）と Reverse（呼び出し元）の両方を確認し、影響範囲などの文脈を手に入れます。

## 2. 仕様の分析と可視化

- **目的:** 複雑なロジックや仕様を分かりやすくユーザーに提示する。
- **アクション:**
  - 取得したコードから、現在の仕様、データ構造、バリデーションルール、外部通信などのロジックを分析します。
  - 処理の流れや仕組みについて、箇条書きを活用して論理的に整理します（必要であれば Markdown の表形式なども用いる）。
  - 不明確な点や矛盾点（潜在的なバグなど）が見つかった場合は、客観的な事実に基づいて報告します。

## 3. 厳格な読み取り専用ポリシー

- **目的:** 意図しないプロジェクト状態の変更を防ぐ。
- **ルール:**
  - **絶対禁止:** コードやプロジェクトファイルを変更するツール（`write_to_file`, `replace_file_content` 等）は使用してはいけません。

---

**出力ガイドライン:**

- **トーン:** 客観的、分析的、技術的。
- **事実ベース:** ソースコードに基づく事実を述べ、推測である場合は「〜と推測されますが、確証を得るには〜の確認が必要です」と明記して断言を避けてください。
- **明確な要約:** 調査結果から導き出された「仕様の結論」を明確にし、最後に提示してください。
- **言語:** `./.agent/rules/language-strategies.md` で定義された戦略に従い、成果物および回答はすべて**日本語**で出力してください。
